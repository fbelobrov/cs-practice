## 1. Три состояния проекта

Создан `lab03/calc.py`. Каждое расширение сохранено отдельным коммитом:

| Коммит | Состояние | Проверка `calculate(8, 2, operation)` |
| --- | --- | --- |
| `6baefbe` | Сложение | `+` → `10` |
| `a634d29` | Добавлено вычитание | `-` → `6` |
| `7b87232` | Добавлено умножение | `*` → `16` |

Для каждого шага выполнены `git add -- lab03/calc.py` и `git commit -m ...`.
Сообщения: `lab03: create calculator with addition`,
`lab03: add subtraction to calculator`, `lab03: add multiplication to calculator`.

Например, ввод `8` и `2` при операции `"*"` даёт `16.0`.
Операция передаётся отдельно, поэтому программа читает именно два числа.

## 2. Сравнение версий и поиск изменений

Команды выполнены сразу после третьего коммита, когда `HEAD = 7b87232`:

```sh
git log --oneline --stat
git diff HEAD~2 HEAD -- lab03/calc.py
git show HEAD~1
git log -S"def" --oneline -- lab03/calc.py
git blame lab03/calc.py
```

- `git log --oneline --stat` показал историю, краткие сообщения и статистику:
  создание калькулятора добавило 24 строки, вычитание и умножение — по две.
  В общей истории видны и более ранние коммиты практики `lab04`.
- `git diff HEAD~2 HEAD -- lab03/calc.py` сравнил первую и третью версии.
  В результате видны четыре добавленные строки: условия и вычисления для `-` и `*`.
- `git show HEAD~1` показал автора, дату, сообщение и патч коммита `a634d29`:
  добавление вычитания.
- `git log -S"def" --oneline -- lab03/calc.py` нашёл `6baefbe`, где появились
  определения `calculate` и `main`. Опция `-S` ищет изменения количества
  вхождений строки `def`, а не любые изменения рядом с ней и не текст сообщения.
- `git blame lab03/calc.py` показал последний изменявший каждую строку коммит:
  строки вычитания относятся к `a634d29`, умножения — к `7b87232`, основа — к `6baefbe`.

Разница: `log` отвечает «какие коммиты были», `show` — «что содержит выбранный
коммит», `diff` — «чем отличаются два состояния». `blame` показывает происхождение
текущих строк, но сам по себе не объясняет причину изменения.

`HEAD~2` — относительная ссылка: после новых коммитов она обозначает другую
версию. Для воспроизводимого сравнения можно использовать сохранённые SHA:
`git diff 6baefbe 7b87232 -- lab03/calc.py`.

## 3. Восстановление файла

После коммита заметок `25354b4` вручную удалены две строки обработки умножения.
Эти изменения не добавлялись в индекс и не коммитились.

```sh
git status --short
git diff -- lab03/calc.py
git restore lab03/calc.py
git diff --exit-code -- lab03/calc.py
git show HEAD~2:lab03/calc.py
git restore --source=HEAD~2 lab03/calc.py
git diff
git restore lab03/calc.py
git status --short
```

Первый `status` показал ` M lab03/calc.py`: изменена рабочая копия.
Первый `diff` показал удаление условия `operation == "*"` и строки `return a * b`.
После `restore` проверка `diff --exit-code` завершилась с кодом 0: различий нет.

`git show HEAD~2:lab03/calc.py` показал старый файл без изменения рабочей папки.
На этом шаге `HEAD~2 = a634d29`: из-за добавленного коммита заметок это уже
версия с вычитанием, а не первоначальная версия со сложением.
`restore --source=HEAD~2` скопировал эту старую версию в рабочую папку;
`diff` снова показал отсутствие умножения. Последний `restore` вернул умножение,
а `status --short` ничего не вывел: рабочее дерево чистое.

По умолчанию `git restore <файл>` восстанавливает рабочий файл из индекса.
Здесь индекс совпадал с `HEAD`, потому что `git add` после порчи не выполнялся.
`git restore --source=<коммит> <файл>` берёт содержимое из указанного коммита.
Обе использованные формы меняют только рабочий файл; ветка и история не двигаются.
Незакоммиченные изменения выбранного файла при таком восстановлении теряются.
Если их нужно сохранить, сначала следует сделать коммит, stash или копию.

## 4. Ошибочный коммит и его отмена

В `calculate` добавлено деление `return a / b` без проверки нуля.
Изменение сохранено коммитом `9cb4a7a` с сообщением
`lab03: demonstrate unsafe division without a zero check`.

```sh
git log -3 --oneline
python -c "from lab03.calc import calculate; calculate(8, 0, '/')"
git revert --no-edit HEAD
git log -3 --oneline
```

`log` подтвердил наличие ошибочного коммита. Вызов деления на ноль завершился
с кодом 1 и исключением `ZeroDivisionError: division by zero` — дефект воспроизведён.
`git revert --no-edit HEAD` создал коммит `4f1306e` с сообщением
`Revert "lab03: demonstrate unsafe division without a zero check"`.
В теле сообщения Git сохранил полный SHA отменённого коммита.
Опция `--no-edit` принимает стандартное сообщение без открытия редактора.

После отмены в истории остались и `9cb4a7a`, и `4f1306e`, а небезопасное деление
удалено из файла. Умножение проверено повторно: `calculate(8, 2, '*') == 16`.

`revert` создаёт новый коммит с обратным изменением, сохраняя историю.
`git reset --hard <коммит>` передвигает текущую ветку и заменяет индекс и рабочие
файлы состоянием выбранного коммита; незакоммиченные изменения отслеживаемых
файлов теряются. Последующие коммиты перестают входить в историю этой ветки,
хотя могут оставаться доступными через другие ссылки или reflog.
`reset --hard` здесь не выполнялся: для опубликованной истории безопаснее
`revert`, который можно отправить обычным `push` без переписывания общей ветки.

## 5. Тег рабочей версии

```sh
git tag -a v1.0 -m "Рабочая версия калькулятора"
git tag
git show v1.0
git push origin main
git push origin v1.0
```

Создан аннотированный тег `v1.0` на коммите `33d3ad8`.
В этой версии работают сложение, вычитание и умножение; ошибочное деление отменено.
`git tag` вывел `v1.0`. `git show v1.0` показал автора и сообщение тега,
целевой коммит и его изменения. Оба `push` завершились успешно:
ветка обновлена, а для тега Git сообщил `[new tag] v1.0 -> v1.0`.

Ветка — перемещаемая ссылка: при новых коммитах текущая ветка продвигается.
Тег — имя конкретного состояния; при продолжении работы он сам не перемещается.
Поэтому `v1.0` остаётся на проверенной версии, даже когда `main` развивается.
Технически тег можно переустановить, но опубликованные версии так обычно не меняют.
Обычный `git push origin main` не отправляет все теги, поэтому тег отправлен явно.

## 6. Эксперимент в ветке и слияние

После отдельного коммита заметок о теге выполнено:

```sh
git switch -c experiment
# В calculate добавлено деление с проверкой b == 0.
python -c "from lab03.calc import calculate; assert calculate(8, 2, '/') == 4"
git add -- lab03/calc.py
git commit -m "lab03: add safe division in experiment branch"
git switch main
git merge --no-ff experiment -m "lab03: merge experiment with safe division"
git branch -d experiment
git log -4 --oneline --graph
```

`switch -c` создал ветку и переключил на неё. Коммит `8ba2d8a` добавил деление
с проверкой нуля: при нуле возбуждается `ValueError` с понятным сообщением,
которое обрабатывается в `main`. Обычное деление `8 / 2` проверено: результат `4`.

После возвращения в `main` выполнено слияние с `--no-ff`. Оно создало отдельный
коммит `e22ca6d` с двумя родителями: `2014c3d` и `8ba2d8a`.
Без `--no-ff` в этой ситуации Git мог просто передвинуть `main` вперёд,
не создавая коммита слияния. Здесь отдельный merge-коммит сохраняет структуру
эксперимента в истории.

`git branch -d experiment` удалил имя уже слитой локальной ветки.
Её коммит остался доступен через историю `main`. Команда `log --graph`
показала ответвление с `8ba2d8a` и его слияние в `e22ca6d`.
Если бы эксперимент не подошёл, можно было бы вернуться в `main` без слияния:
сама `main` не изменилась бы. Удаление неслитой ветки требует отдельного
осознанного решения; обычный `branch -d` от такого удаления защищает.

Финальное деление запускается командой `python lab03/calc.py "/"`.
При вводе `8` и `2` результат — `4.0`. При вводе `8` и `0` программа
выводит в stderr `Ошибка: Деление на ноль невозможно` и завершается с кодом 1,
без traceback.

Проверены девять сценариев запуска: четыре арифметические операции, ноль и
отрицательный ноль в делителе, отрицательное дробное число, неизвестная операция,
нечисловой ввод. Все проверки прошли. Через `git show <версия>:lab03/calc.py`
дополнительно проверена работа трёх исторических версий и версии тега `v1.0`.

Проверено, что отмена вернула точное содержимое файла до ошибочного коммита,
merge-коммит имеет двух родителей, тег аннотированный и указывает на `33d3ad8`,
а число новых коммитов превышает требуемые восемь. Изменений в `lab04` нет.

Финальные заметки сохраняются отдельным коммитом и отправляются командой
`git push origin main`. Для проверки публикации используются:

```sh
git rev-parse HEAD
git ls-remote origin refs/heads/main refs/tags/v1.0 'refs/tags/v1.0^{}'
git log --graph --oneline --decorate
git status --short
```

SHA `refs/heads/main` должен совпадать с локальным `HEAD`.
У аннотированного тега SHA самого объекта тега отличается от SHA коммита:
строка `refs/tags/v1.0^{}` указывает именно на коммит рабочей версии.
При чистой рабочей папке `git status --short` ничего не выводит.

## Коротко для защиты

- Посмотреть историю: `git log --oneline`; один коммит: `git show <SHA>`;
  разницу двух версий: `git diff <SHA1> <SHA2> -- lab03/calc.py`.
- Убрать незакоммиченные правки файла: `git restore lab03/calc.py`
  (источник по умолчанию — индекс).
- Взять файл из конкретной версии: `git restore --source=v1.0 lab03/calc.py`.
  Это меняет рабочий файл, но не переносит текущую ветку к тегу.
- Отменить выбранный обычный коммит: `git revert <SHA>`; при последующих правках
  возможен конфликт. На этой практике отменялся непосредственно последний коммит.
- `revert` добавляет обратный коммит, `reset --hard` перемещает ветку и заменяет
  индекс и рабочее дерево. Для общей опубликованной истории использован `revert`.
- Тег фиксирует версию; ветка движется при новых коммитах; `merge --no-ff`
  создаёт отдельный коммит слияния.
